# Product Visual Briefs

Status: Product Visual Assets Phase 2 specification
Audience: Product, design, frontend, QA and technical lead

These briefs define what future images should communicate. They do not generate prompts or assets.

## KAVTRIS FieldOps

| Field | Brief |
| --- | --- |
| Product purpose | Organize external teams, services, visits, checklists, evidence and reports. |
| Primary user | Manager or supervisor coordinating external services. |
| Secondary user | Employee using a phone/tablet during a visit. |
| Primary interface | Manager dashboard on laptop or desktop. |
| Optional companion interface | Mobile visit screen. |
| Main workflow to communicate | Schedule -> assigned professional -> check-in -> checklist -> photo evidence -> validation/report. |
| Key visual elements | Today's agenda, service status, checklist progress, photo/evidence indicator, report/history cue. |
| Allowed metrics/data | Active services, scheduled visits, delayed services, incidents, checklist completion, customer/location count. |
| Optional hardware/context | QR Code, NFC tag, smartphone, tablet, subtle service-location context. |
| Device hierarchy | Laptop/desktop primary; phone secondary but clearly readable. |
| Background treatment | Premium business/service context, not machinery or messy site scene. |
| Unique product cue | QR/NFC check-in plus mobile checklist/evidence workflow. |
| Shared family elements | Navy interface chrome, white panels, gold status accents, realistic devices. |
| What must not be shown | Permanent surveillance map, proprietary tracker, industrial machines, robots. |
| Potential misleading implications | Guaranteed real-time tracking, employee surveillance, manufactured hardware. |
| Catalog composition | Laptop dashboard plus phone, with QR/NFC cue inside safe area. |
| Hero composition | More deliberate desktop/mobile composition with larger manager view and clear mobile visit flow. |
| Mobile-safe focal point | Dashboard center-left, phone center-right, QR/NFC not at edge. |
| Replacement priority | Medium-high because it is high impact, not because current image is weak. |

FieldOps strategy:

- FieldOps should set the benchmark for the visual family because it is the current detailed product-page model.
- Preserve current strengths: manager/mobile split, check-in cue, software-first presentation.
- Correct current limitations: improve hero-grade composition and reduce dependence on tiny mockup text.
- Use separate `fieldops-catalog-v1.webp` and `fieldops-hero-v1.webp` in the production phase if review confirms measurable value.

## KAVTRIS Stock & Orders

| Field | Brief |
| --- | --- |
| Product purpose | Control products, suppliers, stock levels, orders, movements and replenishment alerts. |
| Primary user | Shop, warehouse or restaurant stock manager. |
| Secondary user | Employee updating quantities by phone/tablet or scanning labels. |
| Primary interface | Stock dashboard on laptop/desktop. |
| Optional companion interface | Mobile stock movement or supplier order screen. |
| Main workflow to communicate | Low stock alert -> product review -> supplier order -> stock movement -> updated quantity. |
| Key visual elements | Product list, low-stock status, supplier order card, stock movement, quantity counters. |
| Allowed metrics/data | Product counts, stock minimum alerts, supplier order IDs, warehouse/location labels. |
| Optional hardware/context | Barcode scanner, barcode label, standard label printer, tablet. |
| Device hierarchy | Laptop primary; scanner/label as small secondary object. |
| Background treatment | Shop stock room, grocery shelf, warehouse bench or restaurant storage, softened and uncluttered. |
| Unique product cue | Barcode/label plus low-stock and supplier-order flow. |
| Shared family elements | Navy sidebar/header, white dashboard panels, gold alert accents. |
| What must not be shown | Large automated warehouse machines, proprietary terminals, full ERP screens. |
| Potential misleading implications | Guaranteed stock accuracy, complete ERP replacement, KAVTRIS hardware supply. |
| Catalog composition | Dashboard and scanner/label cue in 16:10 safe area. |
| Hero composition | Not required until a detailed product page exists. |
| Mobile-safe focal point | Low-stock card and quantity indicators in center; scanner not critical at edge. |
| Replacement priority | Medium; preserve the current strong communication and fix ratio consistency. |

Clarification:

- The current description is sufficient to create an honest visual.
- Preserve low-stock, supplier and barcode cues from the current asset.

## KAVTRIS Hotel Operations

| Field | Brief |
| --- | --- |
| Product purpose | Connect reception, cleaning, maintenance, guest requests and room status in one organized operation. |
| Primary user | Hotel operations manager or reception supervisor. |
| Secondary user | Cleaning or maintenance staff using mobile/task view. |
| Primary interface | Room/status board on laptop or desktop. |
| Optional companion interface | Mobile staff task screen. |
| Main workflow to communicate | Task created -> team assigned -> in progress -> checklist/incident -> approval -> room available. |
| Key visual elements | Room grid, cleaning status, maintenance request, guest request, team assignment. |
| Allowed metrics/data | Room numbers, task statuses, open requests, priority labels, property/location labels. |
| Optional hardware/context | Phone/tablet only; generic existing hotel desk elements can appear. |
| Device hierarchy | Room status dashboard primary; phone/tablet secondary. |
| Background treatment | Modern hotel/accommodation context, subtle bell/reception cue if useful. |
| Unique product cue | Room status board with cleaning/maintenance/guest request relationship. |
| Shared family elements | Navy/gold interface shell, white cards, realistic device staging. |
| What must not be shown | PMS certification, full reservation system guarantee, proprietary hotel terminal. |
| Potential misleading implications | Integration with every booking/PMS system by default, automated room availability guarantee. |
| Catalog composition | Room grid large enough to be recognized at card size. |
| Hero composition | Not required until a detailed product page exists. |
| Mobile-safe focal point | Room status board centered; staff phone visible but not required for meaning. |
| Replacement priority | Medium. |

Clarification:

- Focus on staff operations, not a guest booking flow.
- Avoid looking like FieldOps with hotel labels by making the room grid/status board the dominant cue.

## KAVTRIS Ops

| Field | Brief |
| --- | --- |
| Product purpose | Organize internal tasks, approvals, documents, requests, deadlines and indicators. |
| Primary user | Operations manager, administrative lead or internal team coordinator. |
| Secondary user | Employee receiving tasks, approvals or alerts. |
| Primary interface | Internal operations dashboard on laptop/desktop. |
| Optional companion interface | Mobile alert/task list. |
| Main workflow to communicate | Request/task created -> responsible assigned -> approval/document review -> deadline/status -> indicator updated. |
| Key visual elements | Approval queue, document cards, responsible owner, deadline/status, internal request board. |
| Allowed metrics/data | Pending approvals, documents reviewed, overdue tasks, team responsibilities, internal requests. |
| Optional hardware/context | Laptop/desktop, phone/tablet for alerts only. |
| Device hierarchy | Desktop dashboard primary; phone secondary only if showing alerts/tasks. |
| Background treatment | Professional office/operations desk, abstracted and quiet. |
| Unique product cue | Approvals plus documents plus responsible people in one internal workflow. |
| Shared family elements | Navy/gold shell, white dashboard panels, structured status cards. |
| What must not be shown | Generic analytics-only dashboard, certification badges, enterprise guarantee claims. |
| Potential misleading implications | Finished enterprise SaaS, unlimited scale, included APIs/integrations in every project. |
| Catalog composition | Approval/document workflow must be visually obvious at card size. |
| Hero composition | Not required until a detailed product page exists. |
| Mobile-safe focal point | Approval queue and document cards centered. |
| Replacement priority | High; it is the weakest current asset. |

Product clarification:

```text
The current product description is sufficient to produce an honest visual if the image focuses on tasks, approvals, documents, deadlines and responsibilities.
```

The gap is not missing functionality; the gap is visual hierarchy. The current asset looks like general business analytics rather than internal operations workflow.

Differentiation:

- Different from FieldOps: internal operations, not external visits or check-ins.
- Different from Stock & Orders: tasks/documents/approvals, not quantities/suppliers/products.
- Different from Customer Portal: internal team workflow, not customer-facing request visibility.

## KAVTRIS Customer Portal

| Field | Brief |
| --- | --- |
| Product purpose | Give customers a simple area to follow requests, documents, messages and service status. |
| Primary user | Customer or authorized external user. |
| Secondary user | Business team managing customer communications. |
| Primary interface | Customer-facing portal on laptop/tablet or phone. |
| Optional companion interface | Business-side request/message overview. |
| Main workflow to communicate | Customer opens request -> sees status -> reads message -> accesses document -> follows appointment/service update. |
| Key visual elements | Request status, message thread, document area, notification, service history. |
| Allowed metrics/data | Synthetic request IDs, generic document labels, fictional customer-safe statuses. |
| Optional hardware/context | Laptop, phone or tablet only. |
| Device hierarchy | Portal interface primary; mobile view can be prominent because customer usage may be mobile. |
| Background treatment | Calm service/business environment with strong privacy-safe feel. |
| Unique product cue | Customer-facing status plus documents/messages. |
| Shared family elements | Navy/gold interface shell, white cards, realistic devices. |
| What must not be shown | Real customer profiles, payment-card data, app-store badges, live account claims. |
| Potential misleading implications | Implemented authentication in production, real customer accounts, payment processing by default. |
| Catalog composition | Customer portal screen with request, document and message modules. |
| Hero composition | Not required until a detailed product page exists. |
| Mobile-safe focal point | Request status and document/message cards centered. |
| Replacement priority | Medium-high. |

Clarification:

- The product concept supports request, document, message and status tracking.
- Avoid showing real identities or implying that a deployed SaaS account system already exists.

## Production Priority

Recommended controlled order:

1. KAVTRIS Ops
2. KAVTRIS FieldOps
3. KAVTRIS KitchenSync
4. KAVTRIS Customer Portal
5. KAVTRIS Hotel Operations
6. KAVTRIS Stock & Orders

Reason:

- Ops is weakest and tests whether the visual system can make a generic concept specific.
- FieldOps validates the highest-impact product and sets the benchmark for hero/catalog separation.
- KitchenSync tests hardware/context discipline.
- Customer Portal tests privacy-safe customer-facing visuals.
- Hotel and Stock can follow after the system is proven.
